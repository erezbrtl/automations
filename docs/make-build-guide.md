# הנחיות לבניית אוטומציה ב-Make

מסמך עבודה. הוא נכתב כדי שאפשר יהיה לשבת מולו ולבנות תרחיש אמיתי מההתחלה
ועד הסוף, בלי לחפש כלום באמצע. הוא גם מתאים כחומר עזר לסדנה - החלק הראשון
הוא השיטה, החלק השני הוא בנייה מלאה של דוגמה אחת, והשאר הוא שלדים וכללים.

הדוגמה שנבנית כאן במלואה היא הראשונה מארבע הדוגמאות שבאתר
(`resources/examples.html`) - הליד שנכנס ב-23:47. אותו מבנה בדיוק חוזר
בשלוש האחרות.

---

## 1. לפני שנוגעים ב-Make

### לבחור תהליך אחד

תהליך מתאים לאוטומציה עונה על חמשת התנאים האלה. אם אחד מהם חסר, לרוב עדיף
לבחור תהליך אחר ולא להילחם.

| תנאי | השאלה שבודקת אותו |
|---|---|
| חוזר | קורה לפחות כמה פעמים בשבוע, באותו אופן |
| טריגר ברור | יש רגע מוגדר שבו התהליך מתחיל. לא "כשנזכרים" |
| קלט כתוב | המידע קיים כטקסט או כשדה, לא בראש של מישהו ולא בשיחת טלפון |
| החלטה פשוטה | מה שצריך להחליט אפשר להסביר בשלושה משפטים |
| יעד מוגדר | ברור לאן התוצאה נכנסת - גיליון, משימה, הודעה, מייל |

פסילה מהירה: תהליך שדורש שיקול דעת אנושי בכל מקרה, תהליך שקורה פעם בחודש,
תהליך שהקלט שלו הוא שיחת טלפון או פגישה, ותהליך שהתוצאה שלו יוצאת ללקוח
בלי שאף אחד יראה אותה ואי אפשר להרשות בו טעות.

### לכתוב את התהליך במשפט אחד

לפני שפותחים את Make, לכתוב את זה על נייר:

> **כש**\_\_\_\_ **קורה**, לקחת \_\_\_\_, להחליט \_\_\_\_ לפי \_\_\_\_,
> ואז \_\_\_\_ ו-\_\_\_\_.

בדוגמה שנבנה כאן:

> כשמגיעה פנייה חדשה מהטופס באתר, לקרוא את מה שנכתב, לזהות במה מדובר ומה
> רמת הדחיפות, לשלוח ללקוח תשובה ראשונה עם שאלת המשך, לרשום שורה בגיליון
> הלידים, ולפתוח משימת מעקב לבוקר.

אם אי אפשר לכתוב את המשפט הזה, התהליך עוד לא בשל לבנייה.

## 2. מילון Make

עשרה מונחים שמכסים כמעט הכל.

| מונח | מה זה |
|---|---|
| Scenario | התרחיש. האוטומציה עצמה, שרשרת המודולים |
| Module | שלב בודד בשרשרת. כל עיגול על הקנבס |
| Trigger | המודול הראשון. מתחיל את התרחיש |
| Instant trigger | טריגר שרץ ברגע שקורה משהו, דרך Webhook |
| Polling trigger | טריגר מסוג Watch, שבודק כל כמה זמן אם יש חדש |
| Bundle | פריט מידע אחד שעובר בשרשרת. מייל אחד, שורה אחת, פנייה אחת |
| Mapping | לקיחת שדה מפלט של מודול קודם והכנסתו לשדה במודול הבא |
| Router | פיצול לכמה מסלולים במקביל או לפי תנאי |
| Filter | תנאי על הקו בין שני מודולים. מה שלא עומד בו נעצר |
| Operation | יחידת החיוב של Make. כל הרצה של מודול היא Operation אחת |

עוד שלושה שיגיעו בהמשך: **Iterator** מפרק מערך לפריטים, **Aggregator**
מאחד פריטים בחזרה, ו-**Data store** הוא טבלה קטנה של Make עצמו לשמירת מצב
בין הרצות.

## 3. הכנות

לפני הבנייה, לוודא שיש גישה לכל מה שהתרחיש נוגע בו. חיבור שנתקע באמצע
הבנייה שובר את הרצף.

- חשבון Make פעיל, וארגון אחד שבו יושבים כל התרחישים
- החיבורים (Connections) לכל שירות שנוגעים בו - Google, מייל, ווטסאפ
- מפתח API לספק ה-AI, שמור בחיבור של Make ולא מודבק בתוך שדה טקסט
- הגיליון או הטבלה שאליהם כותבים, כבר קיימים, עם שורת כותרות סופית
- מספר טלפון וכתובת מייל לבדיקות, שאינם של לקוח אמיתי

לגבי ווטסאפ, שווה לדעת מראש: שליחת הודעה יזומה ללקוח שלא כתב בעשרים
וארבע השעות האחרונות מחייבת תבנית מאושרת מראש אצל הספק. תשובה בתוך החלון
הזה היא טקסט חופשי. זה משפיע על מה שאפשר לבנות, אז כדאי להחליט את זה
בהתחלה ולא בסוף.

## 4. הבנייה המלאה - הליד שנכנס ב-23:47

שבעה מודולים. זה כל התרחיש.

| # | מודול | תפקיד |
|---|---|---|
| 1 | Webhooks > Custom webhook | קולט את הפנייה מהטופס |
| 2 | Tools > Set multiple variables | מנקה ומסדר את השדות |
| 3 | Anthropic Claude > Create a Message | קורא, מסווג ומנסח |
| 4 | JSON > Parse JSON | הופך את תשובת ה-AI לשדות |
| 5 | Router | מפצל לשלושה מסלולים |
| 6a | הודעה ללקוח | תשובה ראשונה |
| 6b | Google Sheets > Add a Row | השורה בגיליון |
| 6c | Google Tasks > Create a Task | משימת המעקב |

### מודול 1 - הטריגר

`Webhooks > Custom webhook`. יוצרים webhook חדש, מעתיקים את הכתובת, ומכניסים
אותה כיעד הטופס באתר. באתר הזה זה השדה `formEndpoint` בקובץ
`assets/js/config.js`.

אחרי היצירה, Make ממתין לקריאה ראשונה כדי ללמוד את מבנה הנתונים. שולחים
פנייה אחת אמיתית מהטופס, וה-webhook קולט את השדות. בלי הצעד הזה אין מה
למפות בהמשך.

### מודול 2 - ניקוי

`Tools > Set multiple variables`. לא חובה, אבל הוא מה שהופך תרחיש קריא
לתרחיש שאפשר לתחזק. כאן מגדירים שמות אחידים לשדות ומטפלים בחסרים:

| משתנה | ערך |
|---|---|
| `lead_name` | `{{trim(1.name)}}` |
| `lead_phone` | `{{trim(1.phone)}}` |
| `lead_text` | `{{ifempty(1.process; "לא נכתב פירוט")}}` |
| `lead_time` | `{{formatDate(now; "DD/MM HH:mm")}}` |

מכאן והלאה ממפים רק מהמשתנים האלה, לא מה-webhook ישירות. אם מבנה הטופס
משתנה, מתקנים מודול אחד במקום שבעה.

### מודול 3 - שלב ה-AI

`Anthropic Claude > Create a Message`. אם האפליקציה לא זמינה בחשבון, אפשר
לעשות את אותו הדבר עם `HTTP > Make a request` - הפרטים בסוף הפרק.

**Model:** `claude-opus-5`

**System prompt** (קבוע, לא משתנה בין הרצות):

```
אתה עוזר של עסק ישראלי קטן שמטפל בפניות נכנסות מהאתר.
המשימה שלך היא לקרוא פנייה אחת ולהחזיר עליה מידע מסודר.

תמיד תחזיר JSON תקין בלבד, בלי טקסט לפניו ואחריו, לפי המבנה:
{
  "topic": "הנושא במילה עד שלוש",
  "urgency": "גבוהה" | "בינונית" | "נמוכה",
  "reply": "תשובה ראשונה ללקוח",
  "needs_human": true | false
}

כללים לשדה reply:
- לפתוח בשם הפרטי של הפונה
- לאשר שהפנייה התקבלה ולציין במה היא עוסקת
- לשאול שאלה אחת שתקדם את הטיפול
- עברית פשוטה, בלי סופרלטיבים ובלי סימני קריאה
- עד ארבעים מילים
- לא להתחייב למחיר, לזמן אספקה או לזמינות

urgency היא גבוהה רק אם הפונה כתב במפורש שזה דחוף או ציין מועד קרוב.
needs_human הוא true אם הפנייה כוללת תלונה, בקשת ביטול, או משהו שלא
הבנת. במקרה כזה reply צריך להיות אישור קבלה בלבד, בלי שאלות.
```

**User message** (משתנה בכל הרצה):

```
שם: {{2.lead_name}}
טלפון: {{2.lead_phone}}
מה נכתב: {{2.lead_text}}
```

**Max tokens:** 1000 מספיקים בגדול לתשובה בגודל הזה.

שלוש הערות על השלב הזה, וזה החלק שהכי קל לפספס:

1. **הפרדה בין קבוע למשתנה.** כל ההנחיות יושבות ב-system, רק הנתונים
   יושבים בהודעת המשתמש. זה מה שהופך את התוצאה ליציבה בין הרצות.
2. **פלט מובנה, לא טקסט חופשי.** מבקשים JSON בשדות קבועים. בלי זה השלב
   הבא לא יכול לעבוד, וכל שינוי קטן בניסוח של המודל שובר את התרחיש.
3. **דלת יציאה.** השדה `needs_human` הוא מה שמאפשר לתרחיש להגיד "אני לא
   נוגע בזה". אוטומציה בלי דלת יציאה תשלח בביטחון גם תשובה שגויה.

### מודול 4 - פירוק התשובה

`JSON > Parse JSON`. מזינים בשדה ה-JSON את הפלט של מודול 3, ומגדירים
Data structure עם ארבעת השדות. מכאן `topic`, `urgency`, `reply` ו-
`needs_human` הם שדות רגילים שאפשר למפות.

### מודול 5 - הפיצול

`Router` עם שלושה מסלולים. על המסלול הראשון בלבד יושב Filter:

```
needs_human   Equal to   false
```

שני המסלולים האחרים רצים תמיד. כלומר: הגיליון והמשימה נוצרים בכל מקרה,
וההודעה האוטומטית ללקוח נשלחת רק כשהמודל היה בטוח מספיק.

### מודול 6a - התשובה ללקוח

מודול השליחה של הערוץ שבו משתמשים, עם `{{4.reply}}` כגוף ההודעה
ו-`{{2.lead_phone}}` כיעד.

### מודול 6b - הגיליון

`Google Sheets > Add a Row`, לגיליון הלידים:

| עמודה | ערך |
|---|---|
| תאריך | `{{2.lead_time}}` |
| שם | `{{2.lead_name}}` |
| טלפון | `{{2.lead_phone}}` |
| נושא | `{{4.topic}}` |
| דחיפות | `{{4.urgency}}` |
| מקור | `אתר` |
| טופל | `לא` |

### מודול 6c - המשימה

`Google Tasks > Create a Task`:

- **Title:** `לחזור ל-{{2.lead_name}} - {{4.topic}}`
- **Notes:** `{{2.lead_phone}} · דחיפות {{4.urgency}} · נפתח ב-{{2.lead_time}}`
- **Due:** מחר בבוקר

### אם אין אפליקציית Claude בחשבון

`HTTP > Make a request` עושה את אותו הדבר:

- **URL:** `https://api.anthropic.com/v1/messages`
- **Method:** POST
- **Headers:** `x-api-key` עם המפתח, `anthropic-version` בערך
  `2023-06-01`, ו-`content-type` בערך `application/json`
- **Body type:** Raw, JSON

```json
{
  "model": "claude-opus-5",
  "max_tokens": 1000,
  "system": "כאן נכנס ה-system prompt",
  "messages": [
    { "role": "user", "content": "כאן נכנסים הנתונים" }
  ]
}
```

התשובה חוזרת בשדה `content[0].text`, ואותו מעבירים למודול ה-Parse JSON.

## 6. שבעה כללים

1. **תרחיש אחד, עבודה אחת.** תרחיש שמנסה לטפל בלידים וגם בחשבוניות הוא
   תרחיש שאי אפשר לתקן בלי לשבור חצי ממנו.
2. **הכל עובר דרך שלב ניקוי.** מודול המשתנים בהתחלה הוא ההבדל בין תיקון
   של דקה לתיקון של שעה.
3. **שם לכל מודול.** לחיצה ימנית, Rename. "AI - סיווג פנייה" במקום
   "Anthropic Claude". בעוד חודשיים זה מה שיציל את התרחיש.
4. **בדיקת כפילות לפני כתיבה.** כל מודול שכותב לגיליון או שולח הודעה
   ללקוח צריך לפניו בדיקה שזה לא נעשה כבר. Search Rows או Data store.
5. **Error handler על כל מודול שנוגע בשירות חיצוני.** לחיצה ימנית,
   Add error handler. ההנחיה `Resume` עם ערך ברירת מחדל מתאימה למודול
   שאפשר להמשיך בלעדיו, `Break` מתאימה למודול קריטי. תרחיש בלי error
   handlers נעצר לגמרי בגלל תקלה זמנית אחת.
6. **AI לא מחליט על כסף, על התחייבות ועל פרסום.** הוא מנסח, מסווג ומציע.
   שלושת אלה עוברים דרך אדם.
7. **מידע רגיש לא נכנס לשדה טקסט.** מפתחות ב-Connections בלבד. פרטי לקוח
   רק במה שהתרחיש באמת צריך.

## 7. בדיקה לפני הפעלה

`Run once` מריץ את התרחיש פעם אחת ומראה מה עבר בכל מודול. בודקים בו את
המקרים האלה, בסדר הזה:

| מקרה | מה בודקים |
|---|---|
| פנייה תקינה מלאה | כל שבעת המודולים ירוקים, התוצאה נכונה |
| פנייה בלי טקסט חופשי | ה-AI לא ממציא, `ifempty` תפס |
| פנייה דחופה | `urgency` יצא גבוה, המשימה נפתחה נכון |
| תלונה | `needs_human` יצא true, ההודעה האוטומטית לא נשלחה |
| טקסט ארוך מאוד | לא נחתך באמצע, לא חרג |
| אותה פנייה פעמיים | בדיקת הכפילות עצרה את השנייה |

בכל הבדיקות האלה מספר הטלפון והמייל הם שלכם. אף בדיקה לא יוצאת ללקוח.

אחרי שהכל עבר, מפעילים את התרחיש ומשאירים אותו יום אחד עם `Scheduling`
נדיר יותר מהמתוכנן. עוברים על ה-History למחרת, ורק אז מעלים לתדירות
המלאה.

## 8. תחזוקה

- **פעם בשבוע:** לפתוח את History ולחפש הרצות אדומות
- **פעם בחודש:** לקרוא עשר תשובות שה-AI ניסח, ולוודא שהן עדיין בסגנון
- **בכל שינוי בטופס או בגיליון:** לבדוק את המיפוי לפני ששולחים תנועה
- **Incomplete executions:** להפעיל את האפשרות בהגדרות התרחיש. הרצה
  שנכשלה נשמרת ואפשר להריץ אותה מחדש במקום לאבד אותה

---

## 9. צילומי מסך לאתר

כשמסיימים לבנות תרחיש אמיתי, שווה לצלם אותו. ארבעה צילומים לכל תרחיש:

1. **הקנבס המלא** - כל המודולים מחוברים, אחרי הרצה מוצלחת, עם הסימונים
   הירוקים ומספרי ה-Bundles
2. **שלב ה-AI פתוח** - הפרומפט נראה, בלי מפתחות ובלי שמות לקוחות
3. **התוצאה** - השורה שנכנסה לגיליון או המשימה שנפתחה
4. **ה-History** - רשימת ההרצות עם התאריכים

לפני צילום: להחליף שמות ומספרים אמיתיים בנתוני בדיקה, לסגור לשוניות
אחרות, ולצלם ברוחב מלא. Make בערכת הצבעים הכהה יושב טוב יותר על האתר.

## 10. תקלות נפוצות

| מה קורה | למה | מה עושים |
|---|---|---|
| ה-webhook לא מציג שדות למיפוי | עוד לא הגיעה אליו קריאה | לשלוח פנייה אחת מהטופס בזמן שהוא בהמתנה |
| Parse JSON נכשל | ה-AI החזיר טקסט לפני או אחרי ה-JSON | לחדד ב-system prompt שמחזירים JSON בלבד |
| השדה ריק אף שיש ערך | מיפוי ממודול לא נכון | לבדוק את מספר המודול בסוגריים |
| הגיליון מקבל שורות כפולות | הטריגר קלט את אותו פריט פעמיים | Search Rows או Data store לפני הכתיבה |
| התרחיש נעצר באמצע הלילה | תקלה זמנית בשירות חיצוני | Error handler עם Resume |
| התשובה ללקוח יצאה באנגלית | הנתונים גברו על ההנחיה | לחזור על דרישת העברית בסוף ה-system prompt |
| Operations נגמרות מהר | טריגר בתדירות גבוהה מדי | לדלל את ה-Scheduling, או Filter מוקדם יותר בשרשרת |

## נספח - תבנית פרומפט

לכל שלב AI בתוך תרחיש, בסדר הזה:

```
[תפקיד]     מי אתה ולאיזה עסק אתה עוזר. שורה אחת.
[משימה]     מה בדיוק לעשות עם הקלט הבודד. שורה עד שתיים.
[פלט]       מבנה ה-JSON המדויק, עם הערכים המותרים בכל שדה.
[כללים]     איך לנסח, מה אסור להבטיח, אורך מקסימלי, שפה.
[יציאה]     מתי להחזיר needs_human ומה להחזיר במקרה כזה.
```

הקלט עצמו לעולם לא נכנס לכאן. הוא נכנס בהודעת המשתמש, בשדות מסומנים.
